## Classification scheme

Every row uses one or more current class tags from the following set. Multi-tag rows list one bullet per outcome in the *Final state* column.

| Class                             | Definition                                                                                                                                                                              |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **R** — Redundant                 | Restates an upstream criterion (verbatim, paraphrase, or specialization at a different grain) without adding a user-facing requirement that the upstream entry does not already impose. |
| **D** — Decision                  | States a representational choice the architecture could have made differently. Belongs in a `Decisions` section opened by a `[!QUESTION]` callout.                                      |
| **F** — Framework-level criterion | A user-facing functional requirement that binds the whole framework (T1).                                                                                                               |
| **A** — Aspect-local criterion    | A user-facing well-formedness requirement that binds only a focused theme (T2 theme files), without constraining decisions in other themes.                                             |
| **Id** — Illegitimate (drop)      | Fundamentally unsound or empty; remove entirely; redirect inbound references to manual triage.                                                                                          |
| **If** — Illegitimate (fold)      | Misformulated as a standalone but the rationale is worth preserving; remove and fold into the host decision named in the per-cell *Final state*.                                        |
| **Ir** — Illegitimate (repair)    | Misformulated, over-narrowed, or internally contradictory; rewrite body, label, question, or scope in place to fix the issue, keeping the anchor and location.                          |
| **P** — Property                  | Better framed as a property or refinement embedded in an existing decision rather than a standalone entry.                                                                              |
| **G** — Generalization required   | Should be promoted to a more general criterion or decision than its current scope.                                                                                                      |
| **T** — Tension                   | A recorded conflict or tradeoff between two criteria, with a resolution pattern. Structural metadata about the criteria graph, not itself a criterion.                                  |

`M` and `S` are no longer class tags. Earlier drafts used them as meta-labels for rows that split into several outcomes; the current table expands those rows directly into explicit F/D/A/R/P/etc. bullets.

**"Final state" column.** For multi-tag entries, the cell is a bullet list with one bullet per class tag, naming the concrete action the migration must take. The action vocabulary follows [Step C of the handoff](_handoff-refactor#^step-c):

- *Remove* — delete the entry.
- *Move to X* — copy to X then delete the original.
- *Copy to X* — copy to X, keep the original (used for backup-sourced entries).
- *Create X* — add a new target entry that does not currently exist as a source row.
- *Promote to T1 as X* — move from T2/T3 to T1 with new anchor X.
- *Split into X1, X2, ...* — rewrite the source as multiple outputs.
- *Fold into X* — merge into existing host decision X.
- *Repair: ...* — rewrite in place.
- *Keep* — leave in place; only wording changes.
- *Rename X → Y* — anchor or label change in place.

New dispatch file: `_decisions-to-dispatch.md`; the final theme placement is decided when the dispatch file is processed.

**"Justification" column**: rationale only, no action repetition.

**Closed-question audit note.** Rule 10 below is the governing policy. Pass 8 flagged eight closed phrasings: L152, L351, L357, L358, L467, L505 were classification-created and were reformulated directly; L336, L346, L595 came from source files and carry Step C `Reformulation:` notes.

## Classification coherence rules

These rules are the canonical operational checks for preserving deep structure during Step B and Step C migration. ^classification-coherence-rules

1. **Parent-before-child rule.** If a row can only make sense after another architectural choice has been made, the parent choice must exist as a D or open D. Child schema, enum, validator, and workflow rows do not stand alone; their Final-state bullets name the parent with `Conditional on <host anchor>`, `Candidate enum body for <host anchor>`, or a fold into the parent.
2. **Decision-grain rule.** Each D answers one question at one grain: framework shape, object kind, field schema, enum body, validator rule, workflow rule, or migration policy. If a row mixes grains, split the outcomes or fold lower-grain content into the host.
3. **Mechanism-before-policy rule.** A validation, workflow, or automation policy names the mechanism it checks or uses. Validator rows point at the segment schema, graph structure, registry, enum, or state encoding that makes the rule executable.
4. **Capability-vs-representation rule.** A user-facing capability is not itself a representational decision. Query, audit, explanation, navigation, rendering, and automation classify as F or A only when stated as requirements; the chosen data structure or process that realizes the capability classifies as D.
5. **Closed-vocabulary escalation rule.** Enum bodies do not become autonomous decisions unless the framework has already decided that a closed vocabulary exists at that site. Otherwise they remain candidate enum bodies under an open D.
6. **Alias-before-new-anchor rule.** Before creating a `^bk-*` anchor, check the alias table and the active anchors for another name of the same object, relation, field, workflow unit, or vocabulary. If the referent already exists, record an alias, refinement, or fold rather than creating a new decision.
7. **Derived-artifact rule.** If a row describes an index, view, report, query output, projection, rendered artifact, or generated file, the row states whether it is stored, generated on demand, cached, or only a view over canonical data.
8. **Round-trip rule.** Schema-level D rows should support the operations the architecture claims: validation, rendering, revision, querying, and migration. If a field exists but no operation uses it, flag it as rationale-only, candidate material, or a suspect autonomous decision.
9. **Failure-mode rule.** Each validator or quality rule names the defect it detects. If no defect taxonomy hosts the defect, either add candidate defect-enum content under the validator taxonomy or state that the rule only enforces a local invariant.
10. **Open-question hygiene rule.** Open D rows list real alternatives, not yes/no shells. A binary question remains only when the distinction itself is the design question, as in legitimate ontological-distinction questions.
11. **No hidden promotion rule.** A theme-local D must not silently imply an F. If a local representational choice creates a framework-wide user-facing requirement, add or promote the F explicitly and classify the local mechanism as D.
12. **Operational migration rule.** Every Final-state bullet implies a Step C action: keep, move, copy, create, promote, split, fold, repair, rename, or drop. If the action is unclear, the row is not operational enough for migration.

## Cross-cutting clarifications

### General progression — *what* / *where* / *exact vocabulary* ^three-step-question-decomposition

*Problem*: Several decisions concern the specific vocabulary in an enum. Each *presupposes* that the notion being represented is indeed recorded via an enum. But most of the time, this upstream decision is not introduced explicitly.

This reveals that a general progression should be applied for each notion that matters in the system:

1. **Constitution question** (optional): *What sub-components define the notion?* This is a purely *conceptual* decomposition, which does not yet commit to any encoding. It is only relevant for complex notions that involve multiple dimensions.
   - Example for *warrant*: "what dimensions distinguish one warrant kind from another?" → admissibility regime, evidence type, defeasibility behavior.
   - Example for *revision*: "what dimensions distinguish revision kinds?" → scope of change, propagation priority, target-object kind.
2. **Encoding question**: *Where and how is each sub-component encoded?* For each sub-component identified in step 1, the candidate encodings are at least:
   - a controlled enum field,
   - a free-form prose field,
   - a typed reference to an object of a dedicated kind,
   - a typed relation,
   - an externalized graph entry,
   - a derived property computed by the build.

   The choice is constrained by the upstream criteria (mechanizability, queryability, narrowness of ontology).
3. **Vocabulary question**: *What are the variants?* This question arises only when step 2 selects a closed enum.

The pattern is currently shortcut by several themes: most enum-vocabulary decisions in the active design jump straight to step 3 (the candidate enum entries) without explicitly answering steps 1 and 2.

| Step-3 vocabulary decision                                                       | Step-2 encoding question                                                                                                                                                        | Step-1 constitution question |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `^t3-warrant-kind-enum`                                                          | Implicit at `^t2-warrant-annotation` ("warrant kind on each edge"), but the choice of an enum field rather than a typed sub-object has not been recorded.                       | Missing.                     |
| `^t3-revision-kind-enum`                                                         | Implicit at `^t2-revision-recording`.                                                                                                                                           | Missing.                     |
| `^t3-relevance-kinds-closed`                                                     | Missing. The upstream question is whether relevance needs its own vocabulary at all, given that relations + strategic annotations + dependency graph already exhibit relevance. | Missing.                     |
| `^t3-gain-kind-enum`, open conceptual-effect enum, open epistemic-functions list | Missing.                                                                                                                                                                        | Missing.                     |

Step C should add the missing upstream questions explicitly for each existing enum decision, even when the answer is "field on the edge" or "controlled enum". The convention also resolves enum collisions: two enums collide when they capture the same notion at the same grain.
